# Day 15：Page QA Agent 与页面质量规则

## 今日产出

- 复用并演进 `QualityReportSchema`，覆盖内容、排版、课程连贯、风格、HTML、素材六个维度。
- 问题包含稳定 code、维度、严重程度、证据来源、结构化位置和可执行 `repairHint`。
- `basicLayoutHeuristics` 用确定性代码检查文档合同、安全、文本密度、固定宽度、裁切风险、对比度与素材。
- 一步 `PageQAAgent` 同时消费 PagePlan、PageContentDSL、HTML、VisualBrief 和可选相邻页面上下文。
- `POST /api/pages/qa` 只返回公开事件与报告，不返回修复后的 HTML。
- Seaca 学习工作区显示总分、六维分数、问题位置和修复建议；QA 状态进入聊天 Timeline。
- 独立预览只接收控制器写入的、重新通过 Schema 校验的可选报告。
- 十类稳定失败分类用于回归：内容偏离、难度不匹配、DSL 缺失、课程断裂、文本过载、布局裁切、对比度、风格漂移、HTML 失败、素材不可用。

## 边界决策

### 为什么复用 QualityReport，而不是创建 PageQualityReportV2？

Day 7 的 QualityReport 已经是课程聚合和前后端共享协议。创建第二套近似协议会让 Course、Page QA、Repair 和 UI 产生转换分支。Day 15 直接补齐六维评分、问题位置与修复门槛，使课程级和页面级报告继续共享同一语义。示例与聚合引用校验同步迁移，避免旧文档悄悄漂移。

### 确定性规则和模型分别负责什么？

代码负责能够重复验证的事实：HTML 合同、安全、标签属性、静态文本长度、颜色对比度、素材空值，以及总分、限分和 `shouldRepair`。模型负责内容是否正确、难度是否合适、页面是否承接前后课程，以及视觉方向是否一致。

静态 CSS 只能提示裁切风险，不能证明浏览器中真的发生遮挡。因此 `overflow:hidden` 和固定宽度使用“风险”措辞；像素级结论应在后续 Playwright 多视口几何检测中补充。

### 为什么 QA 不自动执行？

当前结构化模型调用仍有成本且采用批量 HTTP 返回。HTML 完成后由用户显式运行 QA，可以清楚控制调用时机，并保持 UI 状态机简单。未来切换到 Supervisor 或 SSE 后，可以由工作流策略自动触发，而不用重新设计质量面板。

## 评分与修复门槛

- 内容正确 30%
- 排版协调 22%
- 课程连贯 17%
- 风格一致 13%
- HTML 可运行 10%
- 素材可用 8%

确定性或模型 issue 会按维度限分：error 最高 69，warning 最高 84，info 最高 94。出现 error、内容低于 85、排版低于 75 或 HTML 低于 90 时，`shouldRepair` 必须为 true。HTML 合同/安全错误或内容低于 50 时 decision 为 fail；其他可恢复问题为 revise。

## 复盘与面试题

### 1. AI 生成页面的质量评估应该怎样分层？

第一层是输入和协议完整性，验证 PagePlan、DSL、VisualBrief 与当前 pageId、模板 ID 是否一致。第二层是确定性 HTML 检查，包括安全、文档结构、素材属性和可计算的 CSS 风险。第三层是语义 QA，判断事实、难度、课程承接和风格。第四层是工作流决策，由代码合并问题、限分并计算 `shouldRepair`。未来还可以增加真实浏览器几何和截图回归层。

### 2. 为什么要分离 QA Agent 和 Repair Agent？

QA 产出不可变证据，Repair 消费证据并修改派生产物。分离后可以保存每次生成、报告、修复和复检记录，也能限制修复次数与成本。如果同一个 Agent 边检查边修改，它可能掩盖原始问题、自行宣布通过，或把一次失败变成不可审计的黑盒过程。

### 3. 为什么质量控制不能只依赖 Prompt？

Prompt 是概率性约束，无法保证模型每次遵守全部规则，也无法直接观察真实浏览器尺寸、安全边界和缓存篡改。Schema、静态校验、浏览器测量和固定坏案例提供可重复的外部约束。Prompt 负责引导质量，程序负责证明最低条件已经满足。

### 4. 为什么不能只用一个总体分数？

总体分数会让非关键维度抵消致命错误。例如风格和排版很好，但核心知识错误，加权平均仍可能看似合格。六维分数用于解释问题来源，error 与关键阈值则是不可被平均抵消的硬门槛。

### 5. `shouldRepair` 为什么不直接采用模型布尔值？

模型对严重程度的尺度可能随上下文变化。程序根据稳定规则计算 `shouldRepair`，可保证相同报告产生相同工作流分支。模型仍可提出 issue 和 severity，但安全失败、内容低分等门槛由代码强制执行。

### 6. 如何避免静态布局检测过度承诺？

固定宽度、长文本和 overflow hidden 只能证明存在风险。真实溢出应在 375、768、1440 等固定视口读取 scrollWidth、clientWidth 和元素边界，再结合截图确认。报告必须区分“风险”和“已经发生”，否则 Repair Agent 会围绕误报反复修改。

### 7. 怎样让 QA 报告能被 Repair Agent 稳定消费？

每个问题必须包含稳定 code、维度、严重程度、页面 ID、可选 blockId/selector/viewport、位置描述和 repairHint。blockId 只允许引用 DSL 的真实块；模型发明的 blockId 会被丢弃。Repair Agent 后续可以按 code 选择策略，按位置缩小修改范围，再由 Re-QA 验证同一问题是否消失。
