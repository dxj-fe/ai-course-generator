## 2. 面试题与详细答案

### Q1：Tool Calling 和在业务代码中直接调用 API 有什么区别？

直接调用 API 时，调用时机、调用哪个接口以及参数如何构造，都是程序员预先写在确定性控制流里的。Tool Calling 则是应用先向模型声明一组可用工具及其描述和参数 Schema，由模型根据当前任务生成结构化 Tool Call；应用收到 Tool Call 后再校验参数、执行后端函数，并把 Tool Result 返回模型或前端。

因此二者最核心的区别是决策权：Tool Calling 的“选择工具和生成候选参数”发生在模型侧，真正的权限判断、参数校验和副作用执行仍然发生在应用代码中。模型不能直接访问数据库或外部服务，它只能提出调用请求。

### Q2：为什么 Tool Input 和 Tool Output 都需要 Schema？

Input Schema 同时服务于模型和应用。模型根据字段名、描述、类型和枚举生成参数，应用再用同一 Schema 拦截字段缺失、类型错误和越界值。如果 Schema 太宽，模型更容易产生含糊参数，执行代码也需要承担更多猜测。

Output Schema 则保护工具与后续 Agent 之间的数据边界。即使输入合法，工具实现、第三方 API 或数据源仍可能返回结构漂移。执行后再次校验可以阻止坏结果进入模型上下文、工作流状态或前端。双向校验使 Skill 成为真正可组合的能力接口。

### Q3：工具描述写得含糊会导致哪些问题？

模型主要依赖工具名称、description 和 inputSchema 判断何时调用工具。若多个工具描述重叠，模型可能选错工具；描述缺少禁止场景时，模型可能把视觉风格问题交给功能模板工具；描述过度承诺时，模型还可能生成工具根本无法完成的参数。

改进方法是明确“何时使用、何时不要使用、输入是什么、输出能解决什么”，并用容易混淆的成对案例做回归测试。Tool Description 本质上是提供给模型的 Prompt，必须像普通 Prompt 一样版本化和评测。

### Q4：Skill 和 AI SDK Tool 是同一个概念吗？

不是。Skill 是项目内部的领域能力，例如搜索功能模板或校验 CourseIntent；它应独立于具体模型 SDK，可以被普通业务代码、工作流或测试直接调用。AI SDK Tool 是把这项能力暴露给模型的适配层，负责提供模型可理解的 description、inputSchema 和 execute。

将两者分开后，Skill Registry 负责能力注册、输入输出校验和事件记录，AI SDK Tool 只负责协议适配。未来即使更换模型 SDK、把 Skill 接到 MCP，或者改为代码直接调用，核心能力也不需要重写。

### Q5：模型选错工具时应该修改 Prompt、Description、Schema 还是业务代码？

应先用调用记录定位错误发生在哪一层。如果工具选择错误，但参数和执行都正常，优先修改工具名称、Description 或上层 System Prompt；如果工具正确但参数经常错误，应收紧字段名、描述、枚举和 Input Schema；如果参数合法而结果错误，才检查 Skill 的搜索算法或业务数据。

不能只根据一次输出修改代码。应该保存固定输入、Prompt/工具版本、预期工具、实际 Tool Call 和结果，然后重跑完整案例集，确认目标案例修复且旧案例没有退化。

### Q6：如何防止 Tool Calling 进入无限循环？

首先设置明确的最大步骤数或停止条件，不能让模型无限调用工具。其次，每个工具应返回足够明确、可消费的结果，避免模型因为结果含糊而重复查询。还可以限制单个工具的重复次数、总耗时和预算，并通过 `abortSignal` 支持取消。

涉及副作用的工具还需要幂等键或人工审批，防止循环过程中重复执行扣费、发送消息或写数据库。Day 05 Demo 只执行单步 Tool Call；后续实现 Agent Loop 时再显式加入步骤预算和停止条件。

### Q7：哪些 Tool Result 可以展示给用户，哪些只能保留在服务端？

模板名称、匹配理由、公开数据和经过整理的结果摘要通常可以展示。系统 Prompt、私有推理、密钥、内部路径、数据库原始记录、权限信息和第三方服务的敏感错误不能直接进入前端或 Timeline。

日志同样需要最小化。当前 Demo 记录的是结构化模板查询和结果，未来接入用户资料或外部 API 后，应增加字段级脱敏，并让 Timeline 使用专门的公开事件 DTO，而不是直接序列化后端 Tool Result。

### Q8：为什么模板搜索 Skill 不应该直接返回整页 HTML？

模板搜索的单一职责是检索和排序候选模板。如果直接返回整页 HTML，它会同时承担检索、内容生成、样式生成和安全处理，输出体积大、难以校验，也无法被后续 Agent 灵活组合。

返回小型结构化摘要可以让 Planner 或 HTML Engineer 根据模板 ID、结构和推荐理由继续工作，同时减少模型上下文成本。最终 HTML 还需要单独的生成、清理、预览和安全边界，因此应留给后续专门阶段。

### Q9：如何解释“决策在模型，执行在代码”？

模型根据自然语言上下文决定需要哪项能力，并生成符合 Tool Schema 的候选参数；应用代码拥有最终控制权，负责校验、授权、执行、超时、重试、审计和错误处理。即使模型请求了某个工具，应用也可以拒绝或要求人工批准。

这种边界既保留了模型处理模糊意图的优势，也把确定性、安全性和副作用控制留在传统软件系统中。模型是调度建议者，不是直接拥有系统权限的执行主体。
