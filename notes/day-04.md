# Day 04 复盘

## 1. 今天真正理解的概念

### 1.1 Prompt 为什么是模型调用的“软接口契约”

传统函数接口通过参数类型、返回类型和编译器定义确定性契约；Prompt 则通过自然语言约定模型的角色、目标、输入、输出、边界、禁止项和失败处理。它会显著影响模型行为，但不能像类型系统一样保证模型百分之百遵守，因此是“软”契约。

软契约不等于随意文案。工程上仍然需要给 Prompt 命名和版本号，明确输入输出约束，并用 Schema、测试和 bad case 补足它缺少的确定性。当前项目中的 `course-intent-system@1.0.0` 和 `course-intent-user@1.0.0` 就是 Intent Agent 的行为接口。

### 1.2 System Prompt、用户输入、Zod Schema 各自约束什么

- **System Prompt**：约束模型“是谁、负责什么、不能做什么以及应如何输出”。在 Intent Agent 中，它规定只解析课程意图，不生成正文或 HTML，不泄露私有推理，并定义字段默认值和合法范围。
- **用户输入**：描述“这一次具体要处理什么”。它提供课程主题、受众、页数、风格等业务数据，但属于不可信输入，无权改变 Agent 角色、系统边界或输出格式。
- **Zod Schema**：约束“结果是否能进入系统”。它在模型输出后执行确定性的运行时校验，拦截字段缺失、类型错误、非法枚举和越界数值。

三者形成连续防线：System Prompt 引导行为，用户输入提供任务数据，Zod Schema 守住程序的数据边界。Prompt 不能替代 Schema，Schema 也无法表达“不生成 HTML”这类行为职责。

### 1.3 如何记录 bad case，并判断 Prompt 修改是否有效

每个 bad case 至少记录：固定输入、Prompt 版本、模型与运行环境、预期不变量、实际输出、是否通过和后续修正。例如“用户要求返回 `{ data: ... }`”的预期不变量是根对象仍然直接满足 `CourseIntentSchema`。

修改 Prompt 后必须重跑完整固定案例集。只有同时满足以下条件，才能认为修改有效：

1. 目标 bad case 从失败变为通过。
2. 原本通过的案例没有退化。
3. 输出仍通过同一份 Zod Schema，接口结构没有漂移。
4. 默认值、边界值和安全规则保持一致。
5. 结果可由相同 Prompt 版本和测试输入复现，而不是只在一次调用中碰巧正确。

因此，判断标准不是“回答看起来更聪明”，而是可验证的不变量和回归结果。当天的固定案例与实际结果记录在 `notes/day-04-prompt-badcases.md`。

### 1.4 为什么不能在日志或 Agent Timeline 中暴露私有推理链

私有推理可能包含系统 Prompt、用户隐私、内部规则、错误假设或攻击者注入的内容。日志通常会长期保存并被多人或外部系统读取，一旦记录完整推理，就会扩大数据泄露、Prompt 攻击和合规风险。原始推理也不是稳定的产品接口，展示给用户容易造成误解，并让 Timeline 被冗长噪声淹没。

日志和 Timeline 应只展示完成任务所需的可观察事实：阶段、状态、Prompt 版本、traceId、耗时、工具调用结果、错误类型，以及专门生成的简短理由摘要。系统 Prompt、模型原始推理、密钥和完整用户隐私不应进入日志或事件协议。

## 4. 可用于面试的表达

Q：Prompt 工程化与简单“调 Prompt”有什么区别？

A：Prompt 工程化把 Prompt 当作有版本的接口契约。它不仅关注措辞，还定义输入输出边界、变量校验、Schema 对齐、回归案例和可观测性。修改后要用固定 bad case 验证行为变化，才能避免只修复一个样例却破坏其他场景。

Q：如何避免 Agent Timeline 暴露模型的私有推理链？

A：Timeline 只展示阶段、状态、耗时、工具结果和面向用户的简短理由摘要。系统 Prompt、原始模型推理、密钥和完整用户隐私不进入日志或事件协议。
