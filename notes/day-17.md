# Day 17：素材缓存与文本、图片、HTML 合成

## 今日产出

- 页面素材解析先按 PageContentDSL、VisualBrief 和 Image Prompt 版本复用结构化请求集，再查询服务端内容寻址素材缓存；同一页复跑不会因模型措辞漂移重复调用图片接口。
- 缓存键描述实际生图输入和运行版本，而不是只使用 `pageId`；页面内容、风格、比例或模型变化后会自然未命中。
- 缓存条目读取后再次通过共享 Schema 校验，并检查内部 URI 对应的图片文件是否仍然存在。
- 只有 `ready` 素材进入长期缓存。供应商失败形成的 fallback 只服务当前运行，不会变成永久负缓存。
- 缓存损坏、读取失败或写入失败都按 best-effort 降级处理；真实素材已经生成时，缓存故障不会反向让页面失败。
- Image Assets Workflow 通过现有公开 Agent 事件汇总请求集与图片 hit、miss、stale 和 fallback，不把生产 Prompt、缓存摘要或磁盘路径写入公开事件和界面。
- HTML Engineer 继续消费 PageContentDSL、VisualBrief 和当前页素材结果，把背景、角色贴纸与任务卡文字合成为自包含静态 HTML；每个 ready URI 和精确 altText 必须绑定到对应槽位节点，交换槽位会被拒绝。
- Seaca 沿用 `/chat` Timeline、右侧学习工作区与 AssetGallery；缓存是服务端解析细节，不新增路由或平行控制台。

## 实现边界

### 缓存保存什么，不保存什么？

缓存保存两类服务端数据：经过 Schema 校验的结构化 `AssetRequest` 集合，以及 ready 结果的稳定索引。前者让相同页面输入复用第一次编译出的生产 Prompt，后者让相同 prompt + style + aspectRatio + 图片模型复用已批准 URI。真实 PNG、JPEG 或 WebP 仍由 `.data/generated-assets` 统一保存并通过 `/api/assets/[assetId]` 读取。缓存不会复制图片二进制，也不保存原始用户输入、系统 Prompt、供应商密钥或磁盘路径；生产 Prompt 不进入公开 Agent 事件或界面。

fallback 不写入长期缓存。它说明“本次运行可以继续”，不代表“这个输入永远不能生成图片”。如果限流、超时或供应商暂时不可用，下一次素材解析应再次尝试真实生成；否则一次短暂故障会把所有后续运行永久锁定在占位结果上。

### 为什么缓存不能只按 `pageId` 命中？

`pageId` 只标识页面位置，不描述图片内容。同一页面可以修改素材用途、视觉风格、宽高比、透明背景、安全区、供应商或模型。只用 `pageId` 会把旧图片错误复用到新内容。Day 17 使用两级内容寻址：请求集键覆盖完整 Page DSL、VisualBrief 与 Image Prompt 版本；单张素材键覆盖规范化后的生产请求、样式上下文、供应商/图片模型和缓存格式版本。输入事实不变才命中，任一影响输出的事实变化都会未命中。

两级键还解决了一个容易漏掉的问题：ImagePromptAgent 是模型调用，即使页面完全相同，也可能在第二次返回略有差异的 `promptCore`。如果每次都先重新调用 Agent，再按新 Prompt 查图片缓存，“重复生成同一页”就没有确定保证。先缓存已校验请求集可以稳定这层编译结果；Prompt 合同升级时，版本字段又会让旧请求自然失效。

缓存键的职责是判断“是否可以安全复用”，不是展示给用户。公开事件只发送计数和可理解的状态摘要，不发送原始 Prompt 或摘要值，以免让浏览器状态逐渐变成服务端实现细节的镜像。

### 为什么命中后还要检查素材文件？

缓存索引和图片文件有不同生命周期。开发者可能清理 `.data/generated-assets`、迁移运行目录，或者只恢复了索引备份。如果索引仍有 URI 但文件已经不存在，直接返回会让 AssetGallery 和 HTML 预览得到 404。

因此命中是两阶段判断：先找到并校验缓存条目，再用内部素材存储检查 backing file。文件存在才是真正的 hit；文件缺失记为 stale miss，并重新调用图片 Skill。这里不把 stale 当成业务失败，因为系统仍有明确的自愈路径。

### 缓存故障为什么不应该阻塞合成？

缓存优化成本和延迟，但不是课程内容的事实来源。读取到损坏 JSON 时可以按空缓存继续；写入失败时，刚生成的 ready 素材仍然有效；图片供应商失败时，结构化 fallback 仍允许 HTML Engineer 完成页面。只有 Page DSL、素材槽对应关系或 HTML 安全合同不成立时，才应阻断该阶段。

这是一种故障隔离：课程内容、图片生成、缓存持久化和 HTML 合成各有独立责任。辅助设施失败不能升级成核心产物失败，但必须留下公开、可审计且不泄露私密数据的事件摘要。

## 合成数据流

```text
PageContentDSL.assetSlots
  -> Request-set cache lookup
       -> hit: reuse validated AssetRequest[]
       -> miss: ImagePromptAgent, then best-effort request-set write
  -> Ready-asset cache lookup
       -> valid hit: reuse approved AssetGenerationResult
       -> stale or miss: generateImageSkill
            -> ready: return now, then best-effort cache write
            -> fallback: return for this run only
  -> pageAssets controller state
  -> HtmlEngineerAgent
  -> HTML contract + safety + asset reference validation
  -> Seaca learning workspace / sandbox preview
```

缓存没有进入展示组件。API 客户端仍把批量 JSON 转成类型化的页面素材阶段，Task Controller 仍持有 `pageAssets`、`pageHtml` 和 `pageQa`。Timeline 只读取公开 `summary`；AssetGallery 只区分可用图片和显式 fallback。请求集命中只说明服务端复用了已校验的编译结果，不会把生产 Prompt 展示给学习者。以后把 JSON 传输替换为 SSE 时，只需增量追加同一类事件，不需要重新设计页面。

## 文本、背景和角色贴纸如何协作

背景图负责建立氛围，并通过 `safeArea` 为 HTML 标题和正文保留低细节区域。角色贴纸是独立视觉层，需要完整轮廓；供应商无法提供透明通道时，结果会携带警告，HTML 应把它放进边界清楚的容器，不能覆盖正文。任务卡标题、说明、操作文案、参考解析和可访问名称始终来自 PageContentDSL，并以真实 HTML 呈现；只在答错后使用的 `feedback.retry` 继续保存在 DSL 中，不强制堆叠到无脚本静态预览的初始正文。

这种合成方式保留了选择文字、读屏、键盘焦点、响应式重排和 QA 定位能力。图片模型不能生成整页 UI，也不能提供按钮、卡片、导航或课程文字。HTML Engineer 只能使用当前页面批准的内部 URI；未知图片源、远程资源、缺失素材标记或 fallback 标记不完整都必须被拒绝。

## 自动化与真实模型验收边界

自动化测试应证明请求集键稳定、同页复跑不会再次调用 ImagePromptAgent 或图片接口、跨页相同生产请求仍可命中、输入或 Prompt 版本变化未命中、条目损坏安全降级、backing file 缺失后自愈、fallback 不缓存、缓存写入失败不影响 ready 结果，以及双素材 HTML 仍保留全部 DSL 文字和批准 URI。

自动化测试不能充分证明图片主体真的避开文字安全区、角色贴纸没有视觉遮挡，或视觉层级适合目标年龄。这些需要使用真实模型结果，在 375px、768px 和 1440px 视口检查可读性、裁切、横向溢出、贴纸边界和 fallback 表现，并与模型调用成本分开记录。

## 复盘与面试题

### 1. 为什么素材缓存键应该基于内容，而不是基于页面 ID？

核心结论是：缓存键必须描述所有会改变生图结果的事实。`pageId` 只说明素材属于哪一页，不能证明 Prompt、样式、比例、透明要求、安全区或模型相同。

在 ai-course-generator 中，第一级键用完整页面输入和 Image Prompt 版本稳定 `AssetRequest[]`，第二级键再结合生产 Prompt、样式上下文、供应商/图片模型和缓存版本定位 ready 素材。修改页面语义、视觉方向、Prompt 合同或图片模型都会在相应层级自然 miss。这种保守失效优先保证素材正确，再争取命中率。

常见追问是“能不能对 Prompt 做模糊匹配提高命中率”。模糊匹配会让语义相近但布局要求不同的图片误复用，尤其会破坏安全区和透明背景约束。除非引入人工审核或更强的素材检索层，否则生产缓存应保持精确命中。

### 2. 为什么 fallback 不应该写入长期缓存？

核心结论是：fallback 表示一次执行的降级结果，不表示该输入永久不可生成。限流、网络波动、超时和供应商故障通常是暂时的；长期负缓存会在服务恢复后继续返回占位图。

本项目让 fallback 进入当前页的 `pageAssets`，因此 HTML Engineer 可以继续完成安全页面，Timeline 也能说明降级原因。但缓存只接收 ready 结果；下一次点击“重新解析素材”时，失败槽位仍会调用图片 Skill。这在可用性和恢复能力之间取得平衡。

如果担心故障期重复请求，可以在未来增加很短的退避或熔断，但它应与成功素材缓存分开，带明确 TTL，并且不能伪装成 ready 命中。

### 3. 缓存索引命中但图片文件不存在时应该怎么办？

核心结论是：它是 stale miss，不是有效 hit，也不是不可恢复错误。索引只能证明过去生成过，不能证明资源现在仍可读取。

ai-course-generator 的 ready URI 指向服务端 `/api/assets/[assetId]`，真实文件保存在生成素材目录。缓存读取后必须用素材存储能力确认文件存在；缺失时忽略旧条目并重新生成，随后写回新结果。公开事件记录 stale 数量，前端不需要理解文件系统细节。

分布式部署中还要考虑对象存储最终一致性和跨实例可见性。此时存在性检查可能需要短暂重试，但原则不变：只有调用方真正可读取的素材才算命中。

### 4. 为什么缓存写入要采用原子替换？

核心结论是：不能让并发读取者看到只写了一半的 JSON。进程中断、磁盘空间不足或两个请求同时写入，都可能产生截断文件并污染后续所有请求。

常见做法是先在同目录写临时文件，确保完整序列化成功后再 rename 覆盖正式索引。同一文件系统内 rename 通常提供原子可见性。读取端仍要使用 Zod 校验，因为原子写入不能防止旧版本、人工修改或语义不合法的数据。

原子替换并不等于解决全部并发问题。多进程同时读改写仍可能丢失更新；Day 17 的单机训练范围可以接受，生产多实例应迁移到数据库或对象存储索引，并使用事务、乐观锁或唯一键。

### 5. 缓存读取或写入失败时，工作流为什么还能返回 completed？

核心结论是：缓存是性能优化，不是页面能否生成的业务前置条件。只要 Image Prompt、图片 Skill 结果和素材合同有效，缓存异常不应抹掉已经得到的产物。

读取失败时按 miss 继续调用图片 Skill；写入失败时直接返回本次 ready 结果；图片生成失败时返回结构化 fallback。工作流用公开事件说明“缓存不可用但已继续”，而不是把内部异常或路径暴露给 UI。这样用户仍能进入 HTML 生成和 QA，也能通过 traceId 排查服务端日志。

权衡是缓存故障期间成本可能上升，因此监控应关注错误率和命中率。但把成本告警与用户页面失败解耦，通常比让辅助设施成为单点故障更可靠。

### 6. 如何证明背景图和角色贴纸没有取代课程 HTML？

核心结论是同时校验内容、素材映射、安全边界和浏览器语义，而不是只看截图是否相似。

在本项目中，HTML 必须保留 PageContentDSL 的标题、旁白、内容块、要点、互动题目、选项与参考解析，并带 `data-page-id`、`data-block-id`、`data-interaction-type` 和每个 `data-asset-slot-id`。`feedback.retry` 属于答错后的条件状态，不要求在初始静态正文中常显；ready 结果只能使用批准的内部 URI，fallback 必须在对应素材节点留下可审计标记，未知 `img src`、远程资源和脚本会被拒绝。图片只是背景或贴纸，任务卡仍由标题、段落、列表、按钮外观和原生静态互动组成。

自动合同能证明文字和引用存在，却不能完全证明没有视觉遮挡。因此还需要真实视口验收。面试中应明确区分“结构可证明”和“视觉需观察”两种证据，避免把单元测试能力夸大。

### 7. 缓存命中信息应该放在 API 结果、Agent 事件还是素材卡片里？

核心结论是：对用户有诊断价值的汇总进入公开 Agent 事件，缓存实现细节留在服务端。素材本身是否 ready 与它来自新生成还是复用无关，不应为了展示来源改变领域协议。

ai-course-generator 已有 `PublicAgentEvent.summary` 到 `/chat` Timeline 的路径，因此 workflow 只需报告请求集与图片 hit、miss、stale 和 fallback 计数。`chat-app` 继续存储类型化 stage，`AssetGallery` 继续展示图片或降级，不直接消费缓存 API。这样未来改为 SSE 时仍只追加事件，不需要改视觉组件。

如果产品以后需要计费明细，可以增加经过审查的统计协议，但不应把完整 Prompt、缓存键、供应商响应或文件路径塞进事件 `data`。可观测性必须遵守最小公开原则。

### 8. 为什么 Day 17 没有立即实现 single-flight 或分布式缓存？

核心结论是：先解决正确复用、失效和故障隔离，再优化高并发重复请求。single-flight 会把同一进程内同时到达的相同 miss 合并为一次生成，但需要处理调用者取消、共享 Promise 失败、超时和内存清理。分布式缓存还涉及跨实例锁、对象存储、租约和一致性。

当前训练阶段是单机、逐页、手动触发素材解析，原子索引和精确键已经覆盖主要成本问题。提前引入分布式协调会增加远超需求的代码和故障模式。等到多页并发或多实例部署出现真实重复生成证据后，再加入 single-flight、唯一任务键或外部缓存更合适。

常见追问是“两个请求同时 miss 会不会各生成一次”。会，这是当前边界内接受的浪费，但不会破坏正确性。优化顺序应先保证结果可校验，再减少重复工作。
